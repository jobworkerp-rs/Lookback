# データベース移行の運用

この文書は、Lookback 起動時に行う memories データベースの移行と、失敗した場合の操作を説明します。

## 起動時に行われること

Lookback は起動のたびに、memories サイドカーを起動する前に、同梱の移行ツール（`memories-db-migrate`）でローカルの memories データベースを確認します。何を移行するか、どの順序で行うか、再試行してよいかは移行ツールが判断します。

- 移行が不要な場合は確認だけで終わり、そのまま起動します。
- 移行が必要な場合は、起動画面に「データベースの移行を確認・実行中」と表示されます。表示中は処理の完了まで Lookback を終了または再起動しないでください。
- 移行に失敗した場合はサイドカーを起動せず、原因と取れる操作を表示します（下記）。

移行の対象や内容は memories が管理しており、Lookback のバージョンごとに異なります。

## Embedding 空間との違い

データベースの形式変更と、Embedding のモデル・tokenizer・revision・次元・距離の変更は別の移行です。上記の起動時移行や「データベース移行前のバックアップ」の設定を、Embedding 空間変更の承認・バックアップと同一視しないでください。

Embedding の退避・削除・復元・完了判定は memories が管理します。ベクトル保存先や移行マーカーを手動で削除して設定変更を通すことは避けてください。復元は再構築中の通常データベースへの書込みを巻き戻す操作ではありません。

モデルの revision は使用する配布物の識別宣言です。現在のrunnerは重み・tokenizerの取得revisionを固定する設定を提供していないため、宣言を保存しても取得するファイルが固定される保証はありません。識別根拠のない旧設定は `unversioned` として扱われます。

### ローカル空間変更の操作

1. 設定でEmbeddingの変更を保存するとき、memoriesが返す計画を確認します。再生成が必要な場合は、対象件数とバックアップ先を確認して承認します。バックアップなしを選ぶ場合は、中止時にベクトルを破棄して作り直すことを明示承認します。
2. 空間の切替中は通常処理を停止します。再構築保留の段階では通常処理を再開でき、進捗を確認できます。最大シーケンス長などの分割設定は、その試行が完了または中止するまで変更しないでください。
3. 再構築の完了見込みは、移行の確定ではありません。確定操作でmemoriesの検証を行います。件数が不明でも0件とは扱わず、検証が失敗を報告した場合は原因を解消して失敗分を再試行するか、示された件数を明示承認します。
4. 中止はmemoriesが案内する操作に従います。バックアップからの復元と設定の巻戻しが必要な場合もあります。中断後は状態を再確認し、別の試行やバックアップを代用しないでください。

アプリの再起動後に失敗件数が表示されない場合も、失敗が0件になったことを意味しません。状態を再確認し、必要なら再構築を再開してから確定時の検証結果を取得し直します。以前の画面に表示された件数だけで承認しないでください。

移行中はベクトル検索・全文検索（FTS）の双方で結果が部分的になる場合があります。検索が0件でも、対象データが存在しないとは限りません。

画面上部のEmbedding移行通知は、移行マーカーや失敗、対処が必要な書込み拒否（別の空間・次元違い・旧形式のワークフローからの書込み）などの確認事項がある場合に表示します。正常時の「マーカーなし」や拒否0件は表示しません。

元データの更新後に届いた古い生成結果や、以前の再生成試行の結果は、memoriesが正しく破棄したもので対処は不要です。これらは画面上部には表示せず、設定 > 高度な設定の「Embedding 移行の状態」にある「Embedding 書込みの記録」に件数だけを表示します。件数はmemoriesの起動後の累計です。Remote接続ではRemoteサーバーの件数を読み取り専用で表示し、アプリを再起動しても件数は戻りません。表示する記録がない場合、Remote接続では「Embedding 移行の状態」の欄自体を表示しません。

通知の「×」で閉じても移行・再構築は停止しません。同じ画面での定期更新では閉じたままですが、別の移行試行や状態・接続先の変更時には再表示します。画面を移動して戻った場合も再表示されることがあります。

Remote接続ではサーバーの空間・移行状態を参照します。アプリからローカル移行CLIや管理操作を使ってRemoteを変更しません。Remoteの移行はサーバー運用者が行い、アプリでは進捗率を推測して表示しません。

## 移行前のバックアップ

移行で実際にデータベースを変更する場合、移行ツールは変更前にバックアップを作成します。変更のない起動ではバックアップは作成されません。

- 保存先: `<データの保存先>/database-migration-backups/`
- 設定: 設定 > 高度な設定 > 「データベース移行前のバックアップ」
  - 「移行前にバックアップを作成する」: 既定は有効です。空き容量が足りない環境では無効にできますが、その状態で移行に失敗すると元に戻せません。
  - 「保持するバックアップ数」: 既定は 1 です。移行が成功した後、これより古いバックアップは移行ツールが削除します。0 の場合は移行中だけバックアップを保持し、成功後に削除します。
- 移行ツールは自分が作成したバックアップだけを削除します。以前のバージョンの Lookback が作成したバックアップは、このフォルダにそのまま残ります。不要であれば手動で削除してかまいません。

## 移行に失敗した場合

失敗画面には、原因の説明、処理段階、エラーコード、復元点（バックアップの場所）が表示されます。表示されるボタンは原因によって異なります。

| 状況 | 操作 |
| --- | --- |
| 他のプロセスがデータベースを開いている、空き容量が足りない、一時的なエラー | 原因を取り除いてから「データベース移行を再試行」を押します。 |
| 前回の移行が途中で失敗し、復元が必要 | 「移行前のデータを復元」を押し、完了後に「データベース移行を再試行」を押します。復元後もサイドカーは停止したままです。 |
| バックアップなしで実行した移行が途中で失敗した、またはデータベース内の参照に不整合がある | このデータベースは使用できません。「新しい空の保存先で開始」を押し、空のフォルダを選んで初期設定からやり直します。現在のデータは元の保存先にそのまま残ります。 |
| `memory_kind` 導入前の古い形式のデータベース | 「v0.0.7 の移行ツールを開く」から Lookback v0.0.7 を入手し、移行してからこのバージョンを起動します。 |
| より新しいバージョンの Lookback で移行済みのデータベース | 最新の Lookback を使用します。 |
| 移行ツールの同梱物の不整合、移行後の検証失敗など | Lookback の更新または再インストールが必要です。「ログを開く」で詳細を確認できます。 |

移行のログは `<データの保存先>/log/database-migration-*.log` に記録されます。不具合を報告する場合は、このログと失敗画面のエラーコードを添えてください。

## 以前のバージョンからの更新

以前のバージョンの Lookback は、データの保存先の直下に `database-migration-receipt.json` と `database-migration-attempt.json` を作成していました。これらは現在の移行では使われず、更新後に移行が実行されたときに削除されます。手動で削除・編集する必要はありません。
